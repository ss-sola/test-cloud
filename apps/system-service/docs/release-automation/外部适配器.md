# 外部适配器

## GitHub

`GitHubReleaseClientService` 通过受控 transport 封装 Contents、commits、branches、refs、compare、tags 和 Pull Request API。发布流程不调用 `POST /merges`，也不执行本地 Git。

PR 流程固定使用来源 `dev/master`：

1. 读取 `targetBranch` 和 `dev/master` 的 ref，校验 expected SHA；
2. `GET /repos/{owner}/{repo}/pulls` 查询 `state=open`、`head={owner}:dev/master`、`base={targetBranch}` 的 PR；
3. 找到唯一且 `headSha` 相同的 PR 时复用；没有匹配时用 `POST /repos/{owner}/{repo}/pulls` 创建；
4. 创建返回 422 且响应明确表示已有 PR 时重新查询一次，用于对账并发创建；其他 422 校验错误不查询；多个匹配、SHA 漂移或响应结构不可信时 fail closed。

GitHub 返回 `mergeable=false` 或 `mergeableState=dirty` 时，执行器将 GitHub 任务标记为 `blocked`，并在 `manual_intervention` 停止；不会触发 Jenkins、modify-log、Feishu 或 completed。`mergeable=null` 或 `mergeableState=unknown` 不误判为冲突，但仍必须经过人工 PR 门禁。服务端不会自动改写分支或强制合并；冲突由 GitHub 上的授权人员解决并合并，合并后重新发起完整发布 Job。

Git tag 仍以 `dev/master` 当前 SHA 为快照，已存在时跳过创建；真实写操作需要独立 apply gate。dry-run 不发送 tag/PR POST。repository、ref、文件路径、tag 和 SHA 作为协议值传递，适配器仍保留 URL 编码、HTTPS/同源、allowlist、超时、响应大小、有限重试和响应结构约束。

## Jenkins

`JenkinsClientService` 直接使用受控 `fetch` 调用 trigger、queue、build 和 Pipeline text endpoint。`branch` 是 Jenkins 构建分支；它不代表 GitHub PR 的 base 分支。只有新的发布 Job 完成 PR 阶段并继续执行时，Jenkins 才有机会被调用；PR 未合并的旧 Job 不会自动触发 Jenkins。

Jenkins 严格执行：

1. POST 配置的 trigger path；只接受 HTTP 201，body 必须为空，禁止 POST 重试；
2. 从同 origin `Location` 提取本次响应的数字 queue id；
3. 轮询 queue 获取本次 executable number，处理 cancelled/stuck/blocked 和 deadline；
4. 轮询本次 build JSON 至 SUCCESS 或明确失败，不使用 lastBuild；
5. SUCCESS 后请求完整 Pipeline text endpoint，并从 marker 后解析 Pipeline tag。

动态任务 URL、超时、凭据和 tag marker 仍只由服务端配置校验；不拉取第三方仓库、不在本地构建第三方项目。

## 发布 docs 与 AI

发布 docs 只读收集当前 tag 与 GitHub Tags API 返回的上一 tag 之间的 commits，不按 person/author 筛选；ENV diff 通过 GitHub Contents 读取并脱敏，modify-log 通过 GitHub Contents 读取原文并作为发布事实。AI 使用 Token 配置中的 `runtime.ai`，失败时降级为本地事实摘要并标记 `degraded`。

## Feishu

Feishu 输出当前未接通。选中该任务时，在任何远程写操作前进入 blocked，不伪造完成，也不在 PR 未合并时绕过门禁。
