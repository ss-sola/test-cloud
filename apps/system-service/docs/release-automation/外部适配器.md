# 外部适配器

## GitHub

`GitHubReleaseClientService` 通过受控 transport 封装 Contents、commits、Git Data blobs/trees/commits、branches、refs、compare、tags 和 Pull Request API。发布流程不调用 `POST /merges`，也不执行本地 Git。

PR 使用请求中的 `branch` 作为 current/head，`targetBranch` 作为 base：

1. tag 创建后，查询相同 current、target 和 release tag 的 closed PR；唯一且 `merged_at` 非空时，跳过重复的 docs/PR 与人工门禁；
2. 未发现已合并 PR 时，首次发布通过 Contents 创建 update-log；重跑时仅当最新自动 update-log commit 仍是 `branch` HEAD 才以 Git Data replacement commit 替换该 tip，然后读取 current 与 target 的 refs 并校验 expected SHA；
3. `GET /repos/{owner}/{repo}/pulls` 查询 `state=open`、`head={owner}:{branch}`、`base={targetBranch}` 的 PR；
4. 找到唯一且 `headSha` 相同的 PR 时复用；没有匹配时用 `POST /repos/{owner}/{repo}/pulls` 创建；
5. 创建返回 422 且响应明确表示已有 PR 时重新查询一次，用于对账并发创建；其他 422 校验错误不查询；多个匹配、SHA 漂移或响应结构不可信时 fail closed。

GitHub 返回 `mergeable=false` 或 `mergeableState=dirty` 时，执行器将 GitHub 任务标记为 `blocked`，并在 `manual_intervention` 停止；modify-log 已在 PR 前读取并纳入发布 Markdown，不会触发 Jenkins、Feishu 或 completed。`mergeable=null` 或 `mergeableState=unknown` 不误判为冲突，但仍必须经过人工 PR 门禁。服务端不强制合并 PR；新 apply 仅在最新自动 update-log commit 仍是 `branch` HEAD 时，使用 Git Data replacement 改写该 source ref 的可达历史，不改写 `targetBranch`；冲突由 GitHub 上的授权人员解决并合并。新 Job 会通过 closed PR 的 `merged_at` 和发布标题确认合并，再继续后置任务。

新建 Git tag 使用 current branch 当前 SHA；已存在的 tag 保持不可变并复用。没有 update-log 历史时，通过 Contents PUT 将文件首次写入 current branch；后续重跑以 Git Data API 创建 blob/tree/commit，单次 PATCH force-update `refs/heads/{branch}`，replacement commit 的 parent 指向被替换自动提交的 parent。只有 latest update-log commit 是 branch HEAD、且该提交仅修改目标文件时才执行；manual/unrecognized/non-tip 场景 fail closed。所有写操作需要独立 apply gate，创建/ ref mutation 不自动重试；dry-run 不发送写请求。最终 HEAD 检查不能消除检查与 PATCH 间的并发 push 竞态，branch protection 拒绝时不绕过。

## Jenkins

`JenkinsClientService` 直接使用受控 `fetch` 调用 trigger、queue、build 和 Pipeline text endpoint。Jenkins 的 `branch` 参数由 `targetBranch` 提供。首次 apply 在 PR 提交/复用后等待人工合并；合并后的新 Job 检测到对应 PR 已合并后，继续以 targetBranch 构建。

Jenkins 严格执行：

1. POST 配置的 trigger path；只接受 HTTP 201，body 必须为空，禁止 POST 重试；
2. 从同 origin `Location` 提取本次响应的数字 queue id；
3. 轮询 queue 获取本次 executable number，处理 cancelled/stuck/blocked 和 deadline；
4. 轮询本次 build JSON 至 SUCCESS 或明确失败，不使用 lastBuild；
5. SUCCESS 后请求完整 Pipeline text endpoint，并从 marker 后解析 Pipeline tag。

动态任务 URL、超时、凭据和 tag marker 仍只由服务端配置校验；不拉取第三方仓库、不在本地构建第三方项目。

## 发布 docs 与 AI

发布 docs 只读收集当前 tag 与 GitHub Tags API 返回的上一 tag 之间的 commits，不按 person/author 筛选；ENV diff 通过 GitHub Contents 读取并脱敏，发布执行会复用 PR 前准备的 modify-log SQL 快照；独立调用时才由 docs service 自行读取。服务不解析或执行 SQL。AI 使用 Token 配置中的 `runtime.ai`，失败时降级为本地事实摘要并标记 `degraded`。生成的 update-log 提交到 `branch`，随 current→target PR 合并。

## Feishu

Feishu 输出当前未接通。选中该任务时，在任何远程写操作前进入 blocked，不伪造完成，也不在 PR 未合并时绕过门禁。
