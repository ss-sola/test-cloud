# 路由专用 JSON parser 与 Nest 默认 parser 的装配边界

## 问题与触发条件

在 Nest 的 configureApp 阶段为部分接口挂载 `express.json()`，以便使用独立请求体上限。如果直接把该函数挂到路由前缀，Nest 可能因其函数名 `jsonParser` 判断全局 JSON parser 已存在，不再注册默认 parser，导致其他路由的 `@Body()` 变成 undefined。

比较接口迁移时，单独测试该接口不足以发现此问题；必须同时验证不在该前缀内的普通 JSON 接口。

## 解决方式

- 将专用 parser 保存在局部变量中，通过名称不同的中间件（本次为 `compareJsonParser`）调用，再注册到目标路径。
- 专用 parser、错误转换、方法/路径检查和请求体校验只挂在业务前缀下。
- 请求体上限的错误直接转换为安全的统一响应，不能将 parser 的原始消息或正文片段交给公共异常日志。
- 不修改 common-service 的默认 parser 或全局请求体限制。

## 隐私边界

公共访问日志在 response finish 时读取 `req.body`；错误过滤器则会在响应结束前立即记录正文。仅在 finish 清空正文无法保护未匹配路由、错误方法等控制器外异常，因此业务前缀需要提前拒绝这些请求，并为正常命中接口配置不记录原文的专用异常过滤器。

配置全局路由前缀时，遗漏前缀的旧比较地址也必须直接安全返回 404；否则正常带前缀请求受到保护，旧地址却会落入公共 404 过滤器，把正文记录到日志。回归测试需在两种地址中都携带秘密标记验证。

输入校验错误也不能原样输出 class-validator 的 value/target，或记录原始 JSON 解析异常的消息和栈。

## 回归验证

`src/__tests__/content-compare-http.spec.ts` 同时验证：

- 比较接口独立上限、全局前缀与 no-store 响应。
- 前缀外 echo 接口仍收到完整 JSON 请求体。
- 错误方法、未知子路径、错误内容类型、无效 JSON、超限正文和 DTO 错误不泄漏测试秘密。
- 正常返回及失败返回的访问/错误日志均不包含比较原文。

测试引用公共内部过滤器时，以测试运行器可解析的绝对路径动态加载，避免静态跨 src 根目录导入导致 TypeScript rootDir 错误，同时不依赖预先存在的公共构建产物。
