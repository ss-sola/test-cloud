# 工作流实时状态与凭据边界

## SSE 写缓冲水位不是客户端已经掉线

**问题：** `Response.write(frame)` 返回 `false` 只说明当前写缓冲达到水位。包含实际写入矩阵的单帧可能超过 socket 默认水位，快客户端也会触发；若立即销毁连接，客户端会不断重连并反复接收同一个大快照，无法进入后续状态。

**触发条件：** 初始快照或确认事件大于约 16 KiB，仍然小于协议允许的单帧预算；即使网络正常也可能复现。

**解决方式：** 最多允许当前这一帧进入缓冲；记录 blocked，在 drain 后清除。下一次事件或心跳到来时若仍 blocked，则断开该订阅，不增加额外事件队列，由客户端重新读取最新快照。终态和断开统一清理订阅、心跳与监听器；订阅异常不能抛入执行核心。回归入口：`workflow-execution-http.spec.ts`、`workflow-execution-integration.spec.ts`，后者覆盖真实 24 KiB 确认帧。

## 凭据反射检查必须使用实际秘密值

**问题：** 对 `JSON.stringify(outputs)` 做原秘密的字符串匹配会漏掉引号、反斜线等经过 JSON 转义的秘密。收集开始节点凭据时若保留首尾空格，而实际能力调用已 trim，也会漏掉其他能力返回的规范化秘密。

**触发条件：** 例如开始节点 GitHub token 为 `  github-secret  `，AI 返回 `github-secret`；或者 token 为含引号/反斜线的可见 ASCII，输出返回其原值。只检查当前能力自身的凭据无法拦住跨凭据组反射。

**解决方式：** 与实际使用规则一致收集开始节点的 trim 后秘密和 runtime 原秘密；遍历输出真实字符串值与对象键，覆盖嵌套对象和数组，在成功状态接纳与下游分发前拒绝。不要靠序列化文本匹配，也不要仅在 SSE 输出时遮盖，否则下游仍可消费秘密。回归入口：`workflow-execution-server.spec.ts`。

## 订阅计数与回调身份需要一一对应

**问题：** 使用 `Set<listener>` 保存订阅，却对每次注册都增加计数；重复传入同一函数时集合只增加一次，退订无法归还全部计数。

**触发条件：** 同一调用方复用 callback 创建多次订阅，退订后全局额度仍被占用。

**解决方式：** 每次注册使用独立绑定回调作为订阅身份，退订仅删除自己的标识并且幂等；正常结束、监听器抛错和手动退订都使用同一计数规则。回归入口：`workflow-execution-server.spec.ts`。
