## 概述

本 skill 用于对 `docs/plan/` 目录下已完成的实施计划进行验收测试。测试范围覆盖后端接口/方法调用和前端页面交互，测试结果生成 Markdown 报告。

**核心流程**：将主分支切到对应计划的 feature 分支 → 执行测试 → 测试通过则合并回主分支，测试失败则不合并 → 在 `docs/test/` 下生成测试报告。

## 前置检查

1. 列出 `docs/plan/` 下所有 `.md` 文件。
2. 如果用户没有指定计划文件，列出所有计划让用户选择。
3. 读取选定计划，解析任务清单表格（`| # | 任务 | 阶段 | 状态 |`）。
4. **只测试状态为"已完成"的计划**，如果计划状态不是"已完成"则跳过并告知用户。
5. 如果没有任何已完成的任务，直接停止并告知用户"该计划暂无已完成任务可供测试"。

## 分支与 worktree 准备

### 确定计划对应的功能名称

从 plan 文件名提取功能名称，规则与 `plan-excute` 一致：

- 去掉 `.md` 后缀
- 去掉"实现计划""计划"等后缀
- 将中文转为有意义的英文 kebab-case，分支名为 `feature/<功能名称>`

### 检查工作分支状态

1. 执行 `git branch --list feature/<功能名称>` 检查分支是否存在。
2. **如果分支不存在**：
   - 告知用户该计划尚未有对应分支，无法进行测试。
   - 在 `docs/test/` 下生成测试报告，标记为"分支缺失，无法测试"。
   - 停止执行。
3. **如果分支已存在**：
   - 执行 `git log feature/<功能名称>..master --oneline` 检查分支是否落后于 master。
   - 如果输出为空 → 分支已包含 master 所有提交，可以直接测试。
   - 如果输出非空 → 分支落后于 master，提醒用户可能需要先执行 `plan-excute` 完成开发。

### 切换到计划分支

1. **确保主分支干净** — 执行 `git status` 检查 master 是否有未提交修改。如果有，先执行 `git stash` 保存。
2. **切到计划分支**：

```bash
git checkout feature/<功能名称>
```

3. **所有测试操作在主项目目录下进行**，直接在该分支上执行。

## 任务解析

从计划文件中提取任务清单表格，逐行解析：

```markdown
| #   | 任务     | 阶段   | 状态   | 开始时间   | 结束时间   | 耗时 |
| --- | -------- | ------ | ------ | ---------- | ---------- | ---- |
| 1   | 描述文字 | 阶段名 | 已完成 | 2026-07-05 | 2026-07-05 | 2h   |
```

如果有状态是未完成的阶段，则认为该任务未完成，跳过测试。

## 测试策略

### 环境就绪检查

1. **读取端口配置**：从各子项目的 `.env` 文件（`apps/*/` 下）和前端 `vite.config.ts` 中提取实际端口号。
   - 后端：`grep -iE "port|PORT" apps/<service>/.env`
   - 前端：`grep -iE "port" web/NestCloudWeb/vite.config.ts`
   - **禁止猜测常用端口**（如 3000、5173），必须以项目配置为准。
2. **检查端口监听**：用 `netstat -ano | findstr "<port>"` 确认各端口是否有服务在监听。
3. **如果后端/前端未启动**，记录为"环境未就绪"，跳过对应的 API 调用或浏览器交互测试，但仍可执行类型检查、单元测试、lint 等静态验证。

### 后端功能测试

对于纯后端任务（不涉及前端页面），通过 API 调用验证：

1. **识别接口路径**：从计划文件的"文件影响范围"或"详细设计"部分提取涉及的 controller 路由。
2. **构造请求**：
   - 使用 `fetch` 或 HTTP 工具调用后端 API。
   - 后端服务地址从环境变量或配置推断（通常为 `http://localhost:3000` 或对应端口）。
   - 先调用登录接口获取 token，再携带 token 调用业务接口。
3. **验证响应**：
   - HTTP 状态码是否为 200。
   - 响应体是否符合预期格式（`ResponseUtil.success` 包裹的 JSON）。
   - 如果是删除类任务（如移除模块），验证对应接口返回 404 或模块不存在。
4. **单元测试**：如果任务涉及新增/修改 service 方法，运行对应模块的单元测试：
   ```bash
   pnpm --dir apps/<service-name> test
   ```
5. **类型检查**：运行对应服务的类型检查：
   ```bash
   pnpm --dir apps/<service-name> tsgo
   pnpm --dir apps/<service-name> lint
   ```

### 前端页面测试

对于涉及前端页面的任务，使用 `/browse` skill 操控浏览器：

1. **登录**：
   - 前端地址从 `web/NestCloudWeb/vite.config.ts` 中的 `port` 配置读取（如 `http://localhost:<port>`）。
   - 使用管理员账号 `admin` / `123456` 登录。
   - 确认登录成功（跳转到主页或看到用户信息）。
2. **导航到目标页面**：
   - 根据计划中涉及的路由名称，从 `appRoutes.tsx` 查找对应 path。
   - 导航到目标页面（如 `/system/account`）。
3. **验证页面行为**：
   - 页面是否正常加载（无报错）。
   - 列表数据是否正常显示。
   - 增删改查操作是否正常。
   - 如果是删除类任务，验证对应页面不再出现或返回 404。
4. **菜单验证**：检查左侧菜单中是否还有已删除模块的入口。

### 数据库验证

对于涉及数据库变更的任务：

1. 检查 `sql/init.sql` 和 `sql/init_data.sql` 是否有对应的变更。
2. 如有必要，通过 PostgreSQL 连接验证表结构是否正确。

## 测试执行流程

```
1. 解析计划 → 提取已完成任务列表
2. 切换到计划分支
3. 对每个已完成任务：
   a. 判断测试类型（后端 API / 前端页面 / 数据库）
   b. 执行对应测试
   c. 记录测试结果（通过 / 失败 / 跳过）
   d. 如发现异常，记录详细信息和解决建议
4. 汇总所有结果
5. 根据测试结果决定是否合并到主分支
6. 生成测试报告
```

## 测试通过后合并到主分支

如果所有测试均通过（允许"跳过"的任务不计入失败）：

1. **切回 master**：

```bash
git checkout master
```

2. **将 feature 分支合并到 master**：

   优先使用 fast-forward 合并，保持线性历史（单父节点）：

```bash
git merge --ff-only feature/<功能名称>
```

   如果 `--ff-only` 失败（feature 分支与 master 存在分叉，无法快进），则退化为普通合并：

```bash
git merge feature/<功能名称> -m "merge: 合并 <功能名称>"
```

3. **恢复 stash**（如果之前有 stash）：

```bash
git stash pop
```

4. **更新计划文件**：将计划状态标记为"已测试通过"。

## 测试失败不合并

如果任何测试失败：

1. **不合并分支到 master**。
2. **不切回 master**，保留在 `feature/<功能名称>` 分支上，方便后续排查。
3. **更新计划文件**：将测试结果摘要写入计划文件的"测试记录"部分。
4. 在 `docs/test/` 下生成测试报告，明确标注"测试失败，未合并"。

## 注意事项

- 测试前先确认后端服务和前端 dev server 正在运行（尝试 ping 端口）。
- 如果后端/前端未启动，记录为"环境未就绪"，不要强行继续。
- 前端登录时使用 `admin` / `123456`，不要尝试其他凭据。
- 删除类任务（移除模块）的测试重点：确认相关文件已删除、路由已清除、无残留引用。
- 新增类任务（新增功能）的测试重点：确认接口可达、页面可访问、数据可操作。
- 测试过程中发现的问题要如实记录，不要因"计划已完成"而忽略。
- 如果任务涉及多个子系统（如同时改了后端和前端），需要分别测试两端。
- **合并操作在主项目目录执行**，先在 `feature/<功能名称>` 分支上完成测试，再切回 `master` 合并。
- **测试失败时保留在 feature 分支上**，不要切回 master，方便排查问题。
